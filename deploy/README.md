# Kubernetes and Azure

The platform runs on Kubernetes with the same images as Docker Compose. The manifests are plain YAML combined
with Kustomize (built into `kubectl`):

| Folder | What it is |
|---|---|
| [`k8s/base`](k8s/base) | Every component in the `cropconnect` namespace: PostgreSQL and RabbitMQ (StatefulSets with persistent volumes), the six services and the gateway (Deployments), the Aspire dashboard, Mailpit, the Node-RED sensor simulator and the autoscalers |
| [`k8s/overlays/local`](k8s/overlays/local) | Docker Desktop's Kubernetes, with the development secrets; gateway on http://localhost:5000 |
| [`k8s/overlays/azure`](k8s/overlays/azure) | Azure Kubernetes Service (AKS), images from Azure Container Registry, random secrets |
| [`azure`](azure) | PowerShell scripts that create, deploy, stop, start and delete the Azure environment |

## Design

- **Containers from official images.** The services build on `mcr.microsoft.com/dotnet/sdk` and `aspnet`; the
  infrastructure uses the official `postgres`, `rabbitmq`, `busybox` and `nodered/node-red` images and Microsoft's
  Aspire dashboard. Mailpit (`axllent/mailpit`), a development tool, is the only community image.
- **One public entry point.** Only the gateway has a `LoadBalancer` Service (a public IP on Azure). The services,
  the databases and the tools are reachable only inside the cluster; the tools are opened with
  `kubectl port-forward`.
- **Secrets** come from a Kubernetes Secret generated by the overlay, never from the images or the repository.
- **Health probes.** Kubernetes restarts a service whose `/alive` fails and only sends traffic to replicas whose
  `/health` passes. The services speak only HTTP/2 (gRPC), so their probes run `curl --http2-prior-knowledge`.
  Init containers wait for PostgreSQL and RabbitMQ instead of crash-looping while they start.
- **Resource requests and limits** on every container, so the scheduler knows what fits on a node and one service
  cannot starve the others.

## Scalability

| Mechanism | What it does |
|---|---|
| Horizontal Pod Autoscaler ([`autoscaling.yaml`](k8s/base/autoscaling.yaml)) | The gateway, Farms, Orders and Sensors go from 1 up to 3 replicas when their average CPU passes 70m (0.07 vCPU) per replica for 2 minutes, and back to 1 when idle |
| Cluster autoscaler (AKS) | When new replicas no longer fit on the node, AKS adds a second node, and removes it when the load drops |
| Client-side gRPC load balancing | gRPC keeps one long-lived HTTP/2 connection, so a normal Service would send every call to the same pod. The services have headless Services, and the callers resolve every replica through DNS (`ServiceDiscovery__UseDns`) and spread the calls over them |
| Competing consumers | Extra replicas of Sensors and Notifications share the RabbitMQ queue: each message goes to one of them |
| Background workers | Outbox publishers, email dispatch, stock release and reservation expiry take a PostgreSQL advisory lock, so with several replicas only one runs a round at a time: events stay in order and no email is sent twice |

To watch it scale, put load on the catalog and follow the autoscaler:

```bash
kubectl -n cropconnect get hpa --watch
```

```bash
kubectl -n cropconnect run load --rm -it --image=busybox:1.37 --restart=Never -- sh -c "while true; do wget -q -O /dev/null http://api-gateway/api/products; done"
```

## Maintenance

- **Rolling updates.** `deploy.ps1` pushes new images and restarts the Deployments one pod at a time; a new pod
  only receives traffic once its readiness probe passes, so an update does not take the API down.
- **Self-healing.** A crashed or hung pod is restarted (liveness probe); a deleted pod is recreated by its
  Deployment.
- **Database migrations** run on startup; EF Core takes a lock, so two replicas starting together do not apply
  them twice.
- **Logs and traces** of every pod go to the Aspire dashboard; `kubectl logs` shows a single pod.

## Local Kubernetes (Docker Desktop)

Turn on Kubernetes in Docker Desktop (Settings → Kubernetes), stop Docker Compose (same ports), then:

```bash
docker compose --profile simulation build
```

```bash
kubectl apply -k deploy/k8s/overlays/local
```

The end-to-end functional tests run against it as they do against Compose, with Mailpit and the RabbitMQ
management API forwarded to their Compose ports (8025 and 15673). Remove everything with
`kubectl delete namespace cropconnect`.

## Azure (AKS)

Requires the Azure CLI, Docker and kubectl. Names, region and node size are in
[`azure/settings.ps1`](azure/settings.ps1).

```powershell
az login
.\deploy\azure\create.ps1    # once: resource group, registry, AKS cluster, budget alert
.\deploy\azure\deploy.ps1    # build, push and deploy; prints the public URL
.\deploy\azure\stop.ps1      # stop the cluster when it is not needed
.\deploy\azure\start.ps1     # start it again (about 5 minutes)
.\deploy\azure\destroy.ps1   # delete everything
```

`deploy.ps1` generates `k8s/overlays/azure/secrets.env` with random passwords on the first run; it holds the
administrator's password and is never committed.

### Costs

The environment is sized for a student subscription:

| Resource | Cost (approximate) |
|---|---|
| AKS control plane | Free tier |
| 1 node `Standard_D2as_v4` (2 vCPU, 8 GB) | about 0.10 USD per hour, nothing while the cluster is stopped |
| Second node (only while the autoscaler needs it) | about 0.10 USD per hour |
| Load balancer and public IP | about 0.03 USD per hour |
| Container registry (Basic) | about 0.17 USD per day |
| Disks (OS disk, PostgreSQL, RabbitMQ) | a few cents per day |

The sensor simulator runs inside the cluster, so its readings cost nothing extra; scale it to zero when it is
not needed (`kubectl -n cropconnect scale deployment/sensor-simulator --replicas=0`). A budget alert emails the
account at 50 % and 80 % of the monthly budget.
